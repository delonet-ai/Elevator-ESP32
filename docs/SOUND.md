# Звуковая подсистема

Реализована программная часть для текущей трёхэтажной конфигурации: события,
очередь, настройки, NVS и веб-диагностика. Аппаратный модуль ещё не выбран:
прошивка использует отключённый `SoundBackend`, GPIO не назначает и звук
не воспроизводит. Платы не прошивались. Двери и фотореверс ещё не реализованы.

## События и будущие расширения

| ID | Событие | Аргумент | Подключено сейчас |
|---|---|---|---|
| 1 | Запуск | 0 | Да |
| 2 | Отправление | Целевой этаж | Да |
| 3 | Прибытие | Достигнутый этаж | Да |
| 4 | Начало калибровки | 0 | Да |
| 5 | Калибровка сохранена | 0 | Да |
| 6 | Позиция восстановлена по верху | 0 | Да |
| 7 | Ошибка | Код ошибки протокола | Да |
| 8 | Программный STOP | 0 | Да |
| 9 | Двери открываются | Резерв | Нет |
| 10 | Двери закрываются | Резерв | Нет |
| 11 | Препятствие двери | Резерв | Нет |
| 12 | Аварийная остановка | Резерв | Нет |
| 13 | Проверка звука | 0 | Только с готовым backend |

Нулевой ID означает отсутствие события. Этаж передаётся отдельным `uint16_t`,
не номером аудиофайла. Это позволяет позднее менять количество этажей и
сопоставлять событие с сигналом либо голосовой записью без изменения автомата
движения. Это не расширяет текущую модель этажей само по себе.
Будущие метки должны подтверждать прибытие в автомате движения, а затем
генерировать тот же `Arrival`. Дверные события подключаются при реализации дверей.

## Очередь и отказ звука

Очередь ограничена восемью событиями, динамической памяти не использует.
Повторы одинакового события с тем же аргументом объединяются, пока событие
ожидает или воспроизводится. Аварийная остановка имеет высший приоритет;
ошибка, STOP и препятствие — следующий. Они вытесняют обычное воспроизведение
и удаляют ожидающие обычные сообщения. Равный приоритет ждёт завершения.
Обычные сообщения старше 2 секунд и важные старше 5 секунд отбрасываются.
Лимит одного воспроизведения — 15 секунд; превышение останавливает звук
и очищает очередь. Недоступный модуль не накапливает сообщения.

`SoundBackend` предоставляет неблокирующие `poll`, `ready`, `busy`, `start`,
`stop`. `busy` должен учитывать задержку старта оборудования. Реальный драйвер
обязан ограничивать время каждого вызова, обрабатывать отключение оборудования
и владеть только выделенными звуковыми GPIO. Менеджер выполняется в основном
цикле, HTTP-обработчики лишь ставят команды в очередь. Звук не управляет мотором
и не заменяет аварийную цепь. Неблокирующий контракт ещё требуется проверить
с выбранным аппаратным драйвером.

## Настройки и веб

Раздел «Звук»: общее включение, обычные сигналы, громкость 0–100%, сохранение,
загрузка текущих значений и тест. Отключение обычных сигналов оставляет ошибки,
STOP, препятствие и аварийное событие. Общее отключение или громкость 0 глушат
всё. Тест доступен только при готовом модуле, сохранённых включённых настройках
и неподвижном лифте вне калибровки. Подтверждение постановки теста в очередь
не является подтверждением слышимого воспроизведения.

Настройки хранятся отдельной записью версии 1 с контрольной суммой в NVS
`lift-sound/settings`. Успех показывается после записи; сбой сохраняет прежние
активные параметры. Ревизия предотвращает перезапись устаревшей формой.
Текущая JSON-копия профиля движения **не включает звук**.

`GET /api/sound` возвращает настройки, ревизию, готовность, последнее и активное
события, глубину очереди и счётчики ошибок/отброшенных сообщений. `POST /api/sound`
принимает `action=save|test`, `revision`, для сохранения — `enabled`, `routine`,
`volume`. Требуются обычная авторизация и токен `X-Lift-Token`. Основной цикл
повторно проверяет неподвижность, отсутствие блокировок и возраст запроса ≤2 с.
