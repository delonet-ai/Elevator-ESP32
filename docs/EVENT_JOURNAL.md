# Журнал событий базы

Раздел «Журнал событий» в веб-интерфейсе показывает последние 32 записи,
новые сверху. В каждой записи указаны время от запуска базы, событие и
позиция в шагах. Позиция — показание счётчика мотора в момент события;
она сама по себе не подтверждает положение кабины.

Записываются:

- запуск базы и переходы автомата между состояниями;
- ошибки защит и памяти, отказ из-за неизвестной позиции, явный сброс ошибки;
- команда программного STOP;
- наблюдаемые изменения признака движения мотора и верхнего концевика;
- изменения результата веб-калибровки, включая потерю сессии;
- результат обработки запроса параметров движения: сохранение, отказ, ошибка записи.
- появление и прекращение свежих пакетов от пульта (регистрация адреса учитывается отдельно).

Переходы состояний, ошибки и STOP записываются непосредственно при обработке,
поэтому несколько переходов внутри одного прохода цикла сохраняются раздельно.
Признаки движения, концевика и результат веб-калибровки проверяются один раз
за проход основного цикла. Это диагностический журнал, не трассировка импульсов
STEP и не полный аудит всех полученных команд. Отклонённые HTTP-запросы,
не дошедшие до основного цикла, сюда не попадают.

Буфер находится в RAM, запись не использует флеш-память, сеть или динамическое
выделение памяти. При заполнении новые события вытесняют самые старые;
интерфейс показывает число вытесненных записей. При перезапуске журнал очищается.
Время `millis()` оборачивается примерно через 49,7 суток; порядок записей
определяется буфером и номерами, а не сортировкой по времени.

Браузер обновляет журнал раз в две секунды отдельно от телеметрии и команд
калибровки. При ошибке соединения, авторизации или устаревшем снимке старые
записи остаются видимыми с предупреждением; скачивание отключается до
следующего успешного обновления. Новый идентификатор запуска заменяет прежнюю
историю после перезапуска базы.

«Скачать журнал» сохраняет `lift-events.json` из последнего успешно полученного
снимка. Файл содержит формат `elevator-esp32-events`, версию 1, идентификатор
запуска, число вытесненных записей и массив событий. Паролей, токена управления,
IP-адреса и настроек Wi-Fi в файле нет.

## API

`GET /api/events` требует ту же Basic Auth, что и веб-интерфейс. Ответ имеет
`Cache-Control: no-store` и поля:

- `boot`: случайный идентификатор запуска, не токен доступа;
- `age`: возраст снимка основного цикла в миллисекундах;
- `overwritten`: количество вытесненных записей (насыщается на `UINT32_MAX`);
- `events`: до 32 записей, от старых к новым.

Каждая запись содержит `id`, `uptime` (мс), `kind`, `value`, `position` (шаги).

| kind | Событие | value |
|---:|---|---|
| 0 | Запуск | 0 |
| 1 | Состояние | Код `LiftState` из протокола |
| 2 | Ошибка | Код `LiftError`, 0 при явном сбросе |
| 3 | STOP | 0 |
| 4 | Мотор | 0 остановлен, 1 движется |
| 5 | Верхний концевик | 0 свободен, 1 нажат |
| 6 | Веб-калибровка | Код `calibResult` из `/api/status` |
| 7 | Параметры движения | 2 сохранено, 3 отклонено, 4 ошибка записи |
| 8 | Входящий трафик пульта | 0 нет свежих пакетов, 1 пакеты поступают |

HTTP-задача читает неизменяемую копию, опубликованную основным циклом вместе
со статусом примерно каждые 100 мс; к мотору и рабочему буферу она не обращается.

Автотесты проверяют кольцевой буфер, вытеснение, порядок при оборачивании времени,
независимость копий, показ ошибок, смену запуска, устаревшие/невалидные ответы
и экспорт. Проверка на реальном лифте ещё предстоит: сопоставить записи с
поездкой, срабатыванием концевика, STOP и потерей веб-сессии.
